### **مسودة: بروتوكول إدارة الإصدارات باستخدام Git**

---

**المقدمة:** هذه الوثيقة تحدد القواعد والإجراءات الموحدة لاستخدام نظام Git لإدارة الشيفرة المصدرية للمشروع. الهدف هو الحفاظ على سجل تغييرات (history) نظيف، منظم، ومفهوم.

---

### **1. هيكلية الفروع (Branching Strategy)**

سنعتمد على نموذج بسيط وفعال يُعرف بـ **"Git Flow المبسط"**. يتكون من فرعين رئيسيين دائمين، وفروع مؤقتة للميزات والإصلاحات.

*   **`main` (الفرع الرئيسي):**
    *   **الغرض:** هذا الفرع يمثل **النسخة المستقرة والجاهزة للنشر دائمًا**.
    *   **القاعدة:** **يُمنع منعًا باتًا** الدفع (Push) مباشرة إلى هذا الفرع. الطريقة الوحيدة لإضافة كود جديد إليه هي من خلال دمج فرع `develop`.

*   **`develop` (فرع التطوير):**
    *   **الغرض:** هذا هو فرع العمل الرئيسي. يحتوي على آخر التغييرات والميزات التي تم تطويرها والتي هي قيد الاختبار.
    *   **القاعدة:** هذا هو الفرع الذي يتم إنشاء كل الفروع الجديدة منه، ويتم دمجها إليه بعد اكتمالها.

*   **فروع الميزات المؤقتة (`feature/...`):**
    *   **الغرض:** عند العمل على ميزة جديدة (مثل "بناء موديل العملاء")، يتم إنشاء فرع جديد من `develop`.
    *   **تسمية الفرع:** `feature/brief-description` (مثال: `feature/build-clients-module`, `feature/add-dark-mode`).
    *   **دورة الحياة:**
        1.  يُنشأ من `develop`.
        2.  يتم العمل عليه.
        3.  عند اكتماله، يتم دمجه **عودة إلى `develop`**.
        4.  يتم حذفه بعد الدمج.

*   **فروع الإصلاحات العاجلة المؤقتة (`hotfix/...`):**
    *   **الغرض:** لإصلاح خطأ حرج (bug) في النسخة المستقرة الموجودة على `main`.
    *   **تسمية الفرع:** `hotfix/issue-description` (مثال: `hotfix/fix-login-validation-error`).
    *   **دورة الحياة:**
        1.  يُنشأ من `main`.
        2.  يتم إصلاح الخطأ.
        3.  عند اكتماله، يتم دمجه **إلى `main` و `develop` معًا** (لضمان أن الإصلاح موجود في كلا النسختين).
        4.  يتم حذفه بعد الدمج.

### **2. معايير رسائل الـ Commit (Commit Message Standards)**

رسالة الـ Commit الواضحة لا تقل أهمية عن الكود نفسه. سنتبع صيغة موحدة وبسيطة.

*   **الصيغة:** `type(scope): Short description`
    *   **`type` (النوع):** يصف طبيعة التغيير.
        *   `feat:` (ميزة جديدة - Feature)
        *   `fix:` (إصلاح خطأ - Bug Fix)
        *   `docs:` (تغييرات في التوثيق فقط - Documentation)
        *   `style:` (تنسيق الكود، فواصل، إلخ - لا يؤثر على المنطق)
        *   `refactor:` (إعادة هيكلة للكود دون تغيير وظيفته)
        *   `chore:` (مهام روتينية مثل تحديث المكتبات)
    *   **`scope` (النطاق - اختياري):** يحدد الجزء من النظام الذي تأثر بالتغيير.
        *   (مثال: `users`, `database`, `auth`, `invoicing`)
    *   **`Short description` (الوصف):** وصف موجز وواضح للتغيير، يبدأ بفعل مضارع.

*   **أمثلة عملية:**
    *   `feat(clients): add creation and editing functionality`
    *   `fix(auth): resolve password reset bug`
    *   `docs(readme): update project setup instructions`
    *   `refactor(database): optimize queries for properties table`
    *   `chore: upgrade CodeIgniter to version 4.5.1`

### **3. إدارة الإصدارات (Tagging & Releases)**

*   **متى ننشئ إصدارًا جديدًا؟**
    *   يتم إنشاء "وسم" (Tag) جديد **فقط** عندما نقوم بدمج تغييرات مهمة من `develop` إلى `main`.
    *   كل عملية دمج إلى `main` تمثل إصدارًا جديدًا ومستقرًا.

*   **نظام تسمية الإصدارات (Semantic Versioning):**
    *   سنتبع نظام `MAJOR.MINOR.PATCH` (مثال: `v1.2.5`).
    *   `PATCH` (e.g., v1.2.5 -> v1.2.6): يتم زيادته عند إصلاح أخطاء (hotfixes).
    *   `MINOR` (e.g., v1.2.5 -> v1.3.0): يتم زيادته عند إضافة ميزات جديدة لا تكسر التوافق مع الإصدارات السابقة.
    *   `MAJOR` (e.g., v1.2.5 -> v2.0.0): يتم زيادته عند إجراء تغييرات كبيرة وغير متوافقة مع الإصدارات السابقة.
